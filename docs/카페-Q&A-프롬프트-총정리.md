# 카페 Q&A 프롬프트·로직 총정리

보험카페용 Q&A 자동 생성에서 쓰이는 프롬프트와 전체 로직을 한 번에 정리한 문서입니다. **1~7절**은 생성 로직·구조, **8~14절**은 품질 게이트·실패 대응·성과 측정·버전 등 **운영 명세**입니다.

**이 문서의 성격**: 아래 3.1~3.4는 “무슨 역할·어떤 입력·연관 키워드 어디에 넣는지”를 압축한 **구성도**입니다. 실제로 API에 넘어가는 프롬프트는 **수천~만 자 단위**이며, 코드에서 패턴/구조를 랜덤 선택해 긴 지시문에 끼워 넣습니다. 수정할 때는 **3.0 실제 프롬프트 규모**와 **qa-prompt.ts 내 상수/가이드**를 함께 보면 됩니다.

---

## 1. 전체 흐름 (generate-qa API)

```
[요청] productName, targetPersona, worryPoint, sellingPoint, conversationMode, conversationLength, (designSheet, reviewCount 등)
    ↓
[전처리] Google Custom Search 10회 → searchResultsText(그라운딩용), keywordCandidates(폴백용)
    ↓
[키워드] Naver SearchAd keywordstool → searchKeywords(상위 5개, 공백 제거·폴백 재시도) 또는 keywordCandidates 상위 5개
    ↓
[Step 1] 질문 생성 (generateQuestionPrompt) → questionTitle, questionContent
    ↓
[Step 2] 답변 생성 (generateAnswerPrompt) → answerContent
    ↓
[Step 3] 대화형 댓글 (generateConversationThreadPrompt) step=3~totalSteps → conversationThread
    ↓
[선택] reviewCount>0 이면 후기성 문구 (generateReviewMessagePrompt) → 스레드 중간에 삽입
    ↓
[응답] questionTitle, questionContent, answerContent, conversationThread, searchKeywords, usage 등
```

- **검색(Google)**: 그라운딩용 텍스트(`searchResultsText`) + 연관 키워드 후보(`keywordCandidates`) 추출.
- **연관 키워드**: **Naver SearchAd**가 있으면 그 상위 5개가 `searchKeywords`로 쓰이고, 질문/답변 프롬프트에 **반드시 포함** 지시로 들어감. 없으면 Google 후보 상위 5개로 폴백.
- **프롬프트**: `lib/prompts/qa-prompt.ts`에 정의되며, 라우트에서 `QAPromptData` + 단계별 context로 호출.

## 2. 입력 데이터 정리

### 2.1 API 요청에서 오는 값

| 필드 | 용도 |
|------|------|
| `productName` | 상품명 (예: 5세대 실손보험, 암보험) |
| `targetPersona` | 타깃 (예: 30대 남자 자영업자) |
| `worryPoint` | 고객 고민 포인트 |
| `sellingPoint` | 설계사가 강조할 판매 포인트 |
| `answerTone` | 답변 톤: friendly, expert, comparative, persuasive |
| `conversationMode` | true면 Step 3 대화형 댓글 생성 |
| `conversationLength` | 4, 6, 8, 10 중 하나 (댓글 개수) |
| `designSheetImage` / `designSheetAnalysis` | 설계서 이미지·분석 결과 (선택) |
| `reviewCount` | 0이면 후기 없음, 1 이상이면 후기성 문구 개수 |
| `generateStep` | 'question' \| 'answer' \| 'conversation' \| 'all' |

### 2.2 라우트에서 만들어지는 값

| 변수 | 생성 방식 |
|------|-----------|
| `searchResultsText` | Google 검색 10쿼리 결과를 `formatSearchResultsForPrompt`로 요약 (최대 5건, 제목·스니펫 한 줄씩). 질문/답변 **그라운딩**용. |
| `keywordCandidates` | 검색 결과 스니펫에서 `...보험` 패턴 추출 + 부족하면 상품명 기반 패턴(추천, 비교, 보장 내용 등) 추가. |
| `searchKeywords` | **1) Naver SearchAd** 연관 키워드 상위 5개(공백 제거, 실패 시 실손보험 등 폴백). **2)** Naver 실패 시 `keywordCandidates` 상위 5개. **질문/답변에 반드시 넣을 키워드**로 사용. |

## 3. 프롬프트별 구성

### 3.0 실제 프롬프트 규모와 랜덤 주입 요소 (수정 시 참고)

아래는 **실제로 모델에 전달되는 프롬프트 길이**와, **코드에서 매번 랜덤/확률로 선택되어 긴 지시문에 끼워 넣어지는 요소**입니다. 프롬프트가 “간단한 게 아니다”는 것과, **어디를 고치면 어떤 동작이 바뀌는지** 확인할 때 사용하세요.

| 단계 | 대략 프롬프트 길이 | 토큰(추정) | 비고 |
|------|---------------------|------------|------|
| Step 1 질문 | **약 3,000자** | 약 750 | 화자·미션·규칙·연관키워드·그라운딩·입력 데이터·출력 유도 포함 |
| Step 2 답변 | **약 10,000자 이상** | 약 2,500+ | 역할·지침 0~10·예시·입력 정보·출력 형식·주의사항·금지 목록 포함 |
| Step 3 대화 댓글 | **약 2,000~3,500자/회** | 약 500~900 | 턴마다 페르소나·유형·이전 대화·금지 사항 포함 |
| 후기성 문구 | **약 2,500자** | 약 600+ | 후기 패턴 8종 예시 + 지침 포함 |

**라우트 로그에서 확인 가능**: `[Q&A 생성] [Step 1] 질문 생성 프롬프트 길이: 3026 문자 (약 757 토큰)` 등으로 실제 자수·토큰이 찍힙니다.

#### Step 1 질문 — 코드에서 랜덤 주입되는 요소 (`lib/prompts/qa-prompt.ts`)

| 상수/함수 | 개수 | 역할 |
|-----------|------|------|
| `QUESTION_CONCEPTS` | 5종 | 질문자 태도 1개 선택: 의심형, 초보형, 꼼꼼형, 감정호소형, 답정너형 |
| `TITLE_PATTERNS` | 6종 | 제목 스타일 1개 확률 선택: 초간단/어그로(20%), 가격강조(20%), 상품명+의심(20%), 상황강조(20%), 특약질문(10%), 정석(10%) |
| `CONTEXT_NOISE` | 7종 | 문체/상황 노이즈 1개: “핸드폰으로 급하게…”, “꼼꼼하고 예의 바른…”, “걱정 많아 ㅠㅠ…”, “회사 업무 중 몰래…”, “보험 용어 어느 정도…”, “이웃에게 물어보듯…”, “시크한 존댓말” 등 |
| 나이/성별 | — | `targetPersona`에서 정규식으로 추출(예: 30대 → 35세), 나이대별 말투 가이드 분기 |

수정 시: 제목 톤을 바꾸려면 `TITLE_PATTERNS`, 질문자 성격을 바꾸려면 `QUESTION_CONCEPTS`, 말투 분위기를 바꾸려면 `CONTEXT_NOISE`를 편집하면 됩니다.

#### Step 2 답변 — 코드에서 랜덤 주입되는 요소

| 상수/함수 | 개수 | 역할 |
|-----------|------|------|
| `ANSWER_STRUCTURES` | 5종 | 답변 구조 1개: 결론→이유→영업, 공감→분석→제안, 질문반박→팩트→유도, 비교→장점→유도, 설명→예시→유도 |
| `answerTone` 맵 | 4종 | friendly, expert, comparative, persuasive → 각각 톤 문장으로 치환 |
| 공감 문구 맵 | 8종 | 감정 상태별 공감 1개 랜덤(급함, 고민, 궁금, 불안, 혼란, 부담, 확신부족, 긴급) |

지침 블록 자체가 길고 번호가 0~10까지 있으며, “구체적 금액 명시”, “비교 제시”, “가입 유도” 예시가 여러 개 들어갑니다. 수정 시: 답변 구조는 `ANSWER_STRUCTURES`, 톤은 `answerTone` 매핑, 공감 문구는 empathy 맵을 편집하면 됩니다.

#### Step 3 대화형 댓글 — 코드에서 랜덤 주입되는 요소

| 상수/함수 | 개수 | 역할 |
|-----------|------|------|
| `COMMENTER_PERSONAS` | 5종 | 확률로 1명 선택: 원글 작성자(40%), 관심 생긴 제3자(25%), 비교 중인 제3자(15%), 급한 가입희망자(10%), 조건 따지는 제3자(10%) |
| 댓글 유형(고객 턴) | 4종 | 의심/검증, 구체적 비교, 조건 확인, (이미 쪽지 없을 때만) 강력한 가입희망 중 1개 |
| `getDialogueState(currentStep, totalSteps)` | 3단계 | 초반(탐색·조건 확인), 중반(갈등·비교), 후반(확신·가입 의사)로 제약/포커스 문구 변경 |

수정 시: 누가 말하는지 비율은 `COMMENTER_PERSONAS`의 probability, 어떤 종류 댓글인지는 고객 턴의 `commentTypes` 배열을 편집하면 됩니다.

#### 후기성 문구 — 코드에서 주입되는 요소

| 항목 | 개수 | 역할 |
|------|------|------|
| `reviewPatterns` | 8종 | “가입 완료+상품 장점+감사”, “만족도+상품 장점+감사” 등 타입별 예시 1개씩, 나이/성별/상품명 치환 |

수정 시: 후기 톤이나 구성을 바꾸려면 `generateReviewMessagePrompt` 내부의 `reviewPatterns`와 지침 문구를 편집하면 됩니다.

#### 공통으로 들어가는 긴 블록 (모든 단계에서 참조)

- `COMMON_GUIDELINES`: 마침표 금지, 문장 중간 줄바꿈 금지, 출력 형식, 다양성, 문단 구분.  
수정 시: `lib/prompts/qa-prompt.ts` 상단 `COMMON_GUIDELINES` 객체를 편집하면 전체 톤/형식이 바뀝니다.

### 3.1 Step 1: 질문 생성 — `generateQuestionPrompt(data: QAPromptData)`

**역할**: 보험 가입을 고민하는 일반인이 카페에 올리는 **질문글(제목+본문)** 생성.

**입력**:  
`productName`, `targetPersona`, `worryPoint`, `sellingPoint`, `answerTone`, `designSheetImage`, `designSheetAnalysis`, `searchResultsText`, `searchKeywords`

**프롬프트 구조**:
- **화자**: 나이/성별은 `targetPersona`에서 추출, 말투는 나이대별 가이드 + 랜덤 상황 노이즈(`CONTEXT_NOISE`).
- **작성 미션**:
  - 제목: `TITLE_PATTERNS` 중 확률로 하나 선택(초간단/어그로, 가격강조, 상품명+의심, 상황강조, 특약질문, 정석 등).
  - 본문: 설계서(보험료·주요보장) 언급, 질문자 태도는 `QUESTION_CONCEPTS` 중 하나(의심형, 초보형, 꼼꼼형, 감정호소형, 답정너형).
- **공통 규칙**: 마침표 금지, 문장 중간 줄바꿈 금지, 2~3문단, 300~500자 내외.
- **연관 키워드**: `searchKeywords`가 있으면 “연관 키워드 (아래 제목·본문에 **반드시 포함**)”로 넣고, “문맥에 맞게 자연스럽게, 정확히 포함” 지시 추가.
- **그라운딩**: `searchResultsText`가 있으면 “[최근 검색 요약]”으로 넣어 최신/구체 정보 반영 지시(출처·링크 금지).

**출력**: 프롬프트 끝에 “제목: / 본문:” 형식으로 유도. 라우트에서 파싱해 `questionTitle`, `questionContent`로 분리.

---

### 3.2 Step 2: 답변 생성 — `generateAnswerPrompt(data, questionTitle, questionContent)`

**역할**: 해당 상품을 판매하는 베테랑 설계사가 **첫 답글** 작성.

**입력**:  
Step 1과 동일한 `QAPromptData` + `questionTitle`, `questionContent`

**프롬프트 구조**:
- **역할**: 15년차 보험 전문가, 해당 상품 전문가, 보험카페 댓글 스타일.
- **핵심 지침**:
  - 세일즈 모드: 직설적 CTA, 우리 상품 가입 유도, 설계서·검색 정보를 근거로 구체적 숫자 제시, 출처/링크 없음.
  - 고객 호명·공감 → 구체적 답변(금액/조건 명시) → 상품 전문적 설명·경쟁사 비교·리스크 설명 → 비교 제시(현실적 보험료) → 가입 유도.
- **구조**: `ANSWER_STRUCTURES` 중 랜덤(결론→이유→영업, 공감→분석→제안 등). 톤은 `answerTone` 매핑.
- **연관 키워드**: `searchKeywords`가 있으면 “아래 연관 키워드를 **반드시** 답변 본문에 넣어주세요”로 명시.
- **그라운딩**: `searchResultsText` 있으면 최신 정보 반영 지시.
- **형식**: 마침표 금지, 문장 중간 줄바꿈 금지, 2~3문단, 300~500자, 이모티콘은 선택적.

**출력**: 본문만. 라우트에서 제어문자·마크다운 제거, 문단·이모티콘 정리 후 `answerContent`로 사용.

---

### 3.3 Step 3: 대화형 스레드 — `generateConversationThreadPrompt(data, context)`

**역할**: 첫 질문·첫 답변 이후 이어지는 **댓글** 생성. 고객/설계사가 번갈아 나옴.

**입력**:  
- `data`: productName, targetPersona, worryPoint, sellingPoint, answerTone, designSheetAnalysis, searchResultsText (연관 키워드는 여기선 미사용)
- `context`: `initialQuestion`, `firstAnswer`, `conversationHistory`(최근 4개만), `totalSteps`, `currentStep`

**로직**:
- `currentStep % 2 === 1` → **고객 턴**: `COMMENTER_PERSONAS` 확률로 페르소나 선택(원글 작성자, 관심 생긴 제3자, 비교 중인 제3자 등). 댓글 유형(의심/검증, 구체적 비교, 조건 확인, 가입희망 등) 랜덤. 이미 쪽지/상담 요청이 있으면 “강력한 가입희망” 제외. 대화 상태(`getDialogueState`)로 초반/중반/후반 제약.
- `currentStep % 2 === 0` → **설계사 턴**: 고객 마지막 질문에만 집중해 답글, 동문서답 금지, 쪽지/상담 넌지시 유도.

**공통**: 마침표 자제, 문장 중간 줄바꿈 금지. 이전에 다룬 주제는 피하도록 안내.

**출력**: 한 번에 한 댓글 문자열. step=3~totalSteps까지 반복해 `conversationThread` 배열 구성.

---

### 3.4 후기성 문구 — `generateReviewMessagePrompt(data, { productName })`

**역할**: 가입 **후** 설계사에게 감사 인사를 전하는 **고객 후기** 한 편.

**입력**:  
`productName`, `targetPersona`, 기타 QAPromptData. context는 `{ productName }`만 사용.

**프롬프트 구조**:
- 나이/성별은 `targetPersona`에서 추출.
- “가입 완료 + 상품 장점 + 감사” 등 여러 후기 패턴 중 하나를 골라 150~250자 내외로 작성.
- 상품 장점(보험료·보장·가성비) 언급, “앞으로도 문의/추천” 등 관계 유지 문구 포함.
- 마침표 금지.

**사용처**: `reviewCount > 0`일 때만 호출. 생성된 후기는 설계사 마지막 댓글 **바로 다음**에 스레드에 삽입. (설계사가 후기에 답하는 `generateReviewResponsePrompt`는 현재 라우트에서 호출되지 않음.)

## 4. 연관 키워드(검색량 상위) 반영 위치

| 단계 | searchKeywords 사용 여부 | 비고 |
|------|---------------------------|------|
| Step 1 질문 | ✅ 사용 | “상위 1~2개 필수, 제목 최대 1개·질문 본문 최대 2개 (12절)” |

`searchKeywords`는 **Naver SearchAd**에서 오는 상위 키워드가 우선이며, 없을 때만 Google 기반 `keywordCandidates` 상위 5개로 대체됩니다.

## 6. 공통 규칙 (qa-prompt 내 COMMON_GUIDELINES)

- **다양성**: 매번 다른 패턴·구조·표현 사용.
- **문단**: 2~3개, 문단 사이 빈 줄(줄바꿈 2개).

## 8. 품질 게이트 (검수 기준)

생성 결과를 “통과/재생성/폐기” 판단할 때 쓰는 **검수 기준**입니다. 프롬프트 수정·모델 교체 후에도 “무엇이 좋아졌는지/나빠졌는지” 비교할 때 사용합니다.

| 항목 | 질문(Step 1) | 답변(Step 2) | 대화 댓글(Step 3) | 후기 |
|------|--------------|--------------|-------------------|------|
| **자연스러움** | 사람이 쓴 카페 질문글처럼 읽히는가 | 설계사 답글처럼 읽히는가 | 앞뒤 맥락과 말투가 이어지는가 | 가입 후 감사 인사처럼 읽히는가 |
| **광고성** | 홍보글/광고 카피처럼 보이지 않는가 | 과하게 판매 유도만 하지 않는가 | 설계사 댓글이 연속 영업 톤만 아닌가 | 극찬·과장 없이 현실적인가 |
| **정합성** | — | 질문 내용과 답변이 엇나가지 않는가 | 고객 질문에 맞게 답하는가 | — |
| **반복성** | — | 이전 답변과 패턴이 동일하지 않은가 | 이미 다룬 주제·표현이 반복되지 않는가 | 후기 패턴이 매번 비슷하지 않은가 |
| **키워드 과밀도** | 연관 키워드가 억지로 나열되지 않았는가 | 키워드가 문맥에 녹아 있는가 | — | — |
| **후기 진정성** | — | — | — | 조작·작업글처럼 느껴지지 않는가 |

- **재생성/폐기**: 위 항목 중 “문제 있다”고 판단되면 해당 스텝만 재생성하거나, 전체 결과를 폐기하고 조건 변경 후 다시 호출하는 기준을 운영 정책으로 둡니다.
- **자동화**: 길이·키워드 개수 기준 **품질 경고**(`qualityWarnings`)가 응답·usage_logs 메타에 포함됩니다. 재생성/폐기는 운영 정책으로 두고, 추후 규칙 기반 필터를 더 도입할 수 있습니다.

## 9. 실패 케이스 사전

**잘되는 예시보다 “이런 출력은 문제”라고 정의해 두는 게 디버깅·재현에 유리합니다.** 아래는 대표적인 실패 유형입니다.

| 유형 | 설명 | 대응 방향 |
|------|------|-----------|
| 질문이 광고 카피처럼 생성됨 | 판매 포인트가 과하게 들어가 일반인 질문처럼 안 보임 | 질문 프롬프트에서 “일반인 고민” 비중 강화, sellingPoint 노출 최소화 |
| 답변이 지나치게 공격적으로 판매함 | CTA·가입 유도가 과하여 카페 독자·운영 정책에 거부감 유발 | 답변 톤·구조 선택지 조정, “넌지시 유도” 비중 확대 |
| 댓글이 앞 대화와 연결되지 않음 | 고객/설계사 댓글이 이전 맥락을 무시하고 새 주제만 던짐 | conversationHistory 활용 강화, “이전에 다룬 주제 피하기” 지시 강화 |
| 후기 문구가 갑자기 튀어나와 조작처럼 보임 | 설계사 유도 직후 바로 극찬 후기가 나오거나 톤이 과함 | 후기 삽입 위치·조건·톤 규칙 적용 (아래 11절 참고) |
| 키워드 삽입 때문에 문맥이 깨짐 | 연관 키워드를 무리하게 넣어 문장이 어색해짐 | 키워드 밀도·위치 제어 규칙 적용 (아래 12절 참고) |
| 질문자와 댓글 페르소나 말투가 너무 비슷함 | 원글 작성자와 제3자 댓글이 말투·수준이 구분되지 않음 | COMMENTER_PERSONAS별 말투·길이 가이드 차별화 |
| 검색/키워드 실패 시 품질 저하 | Naver SearchAd 실패 후 Google 후보만 쓰이거나, 검색 결과가 빈약함 | 폴백 시 “연관 키워드 수 줄이기” 또는 “키워드 없이 생성” 옵션 검토 |
| persona 추출 실패 | targetPersona에서 나이/성별 파싱 실패 시 기본값(30세 남)만 사용 | 로그로 추출 결과 확인, 특수 페르소나(주부, 신혼부부 등) 케이스 문서화 |

## 10. 단계별 행동 목표 표

전체를 “판매” 한 방향으로만 밀면 광고/자문자답/작업글 느낌이 납니다. **단계별로 목표를 나누어 두면**, 프롬프트 수정 시 균형을 잡기 쉽습니다.

| 단계 | 1차 목표 | 2차 목표 | 피할 것 |
|------|----------|----------|---------|
| **질문** | 진짜 사람이 고민하는 듯 보이기 | 궁금증·상황이 구체적으로 드러나기 | 광고 카피·판매 포인트 과다 노출 |
| **첫 답변** | 신뢰 확보 + 기본 설득 | 구체적 금액·조건·비교로 이해 도움 | 과한 CTA·반박 없는 일방 주장 |
| **고객 댓글** | 추가 궁금증이 자연스럽게 발생 | 페르소나에 맞는 말투·관심사 | 같은 주제·같은 톤 반복 |
| **설계사 댓글** | 고객 질문에 맞게 짧게 답변 | 과하지 않게 다음 행동(쪽지/상담) 유도 | 연속적인 강한 영업 멘트 |
| **후기** | 과장 없이 사회적 증거 보강 | 안심·현실 톤의 짧은 감사 인사 | 극찬형·조작 느낌 |

## 11. 후기 삽입 규칙

현재는 `reviewCount > 0`**이며** `conversationLength >= 6`일 때만 후기성 문구를 생성해 설계사 마지막 댓글 **바로 다음**에 삽입합니다. 아래 규칙이 코드에 반영되어 있습니다.

| 규칙 | 권장 내용 |
|------|-----------|
| **삽입 허용 조건** | 대화 길이(conversationLength)가 일정 이상일 때만 후기 삽입 (예: 6 이상). 너무 짧은 스레드에 후기가 바로 나오면 조작처럼 보일 수 있음. |
| **삽입 위치** | 스레드 **중후반**에만 허용. 설계사가 “쪽지/상담 주세요” 직후에 바로 후기가 오는 구성은 피함. |
| **후기 톤** | “극찬형”보다 “안심형/현실형” 위주. 과도한 상품 찬양·숫자 나열 지양. |
| **후기 이후 설계사 멘트** | 후기가 삽입된 뒤 설계사 추가 영업 멘트는 약하게 하거나 생략. (현재는 후기에 대한 설계사 응답을 생성하지 않음.) |

## 12. 키워드 자연 삽입 규칙 (목표 정책)

현재 구현은 연관 키워드를 질문/답변에 **“반드시 포함”**하도록 지시합니다. **과하게 넣으면 SEO·광고 냄새가 나므로**, 아래 목표 정책이 질문·답변 프롬프트에 반영되어 있습니다.

| 구분 | 현재 | 권장 목표 |
|------|------|-----------|
| **필수 개수** | 5개 모두 반드시 포함 | 상위 1~2개만 필수, 나머지는 가능하면 자연스럽게 |
| **제목** | 연관 키워드 포함 가능 | 제목에는 최대 1개 |
| **질문 본문** | 연관 키워드 반드시 포함 | 본문에 최대 2개 수준, 문맥에 녹이기 |
| **답변 본문** | 연관 키워드 반드시 포함 | 본문에 2~3개 수준, 나열 금지 |

- 키워드 소스(Naver SearchAd 상위 5개)는 유지하되, **“몇 개까지, 어디에, 어떤 톤으로”** 넣을지만 조정하면 자연스러움이 올라갑니다.

## 13. KPI/성과 측정 항목

이 시스템의 목적은 “예쁜 글”이 아니라 **전환·운영 안정성**입니다. 아래 지표를 문서에 두면, 프롬프트·정책 수정을 **데이터 기준**으로 할 수 있습니다.

| 구분 | 지표 예시 | 비고 |
|------|-----------|------|
| **노출·참여** | 제목 클릭률, 답변까지 체류율, 댓글 지속률(몇 턴까지 읽히는지) | 카페/플랫폼에서 수집 가능한 범위에서 정의 |
| **전환** | 쪽지/문의 유도율, 저장·공감 비율 | 목표 전환 액션을 정해 두고 추적 |
| **운영 리스크** | 운영자 삭제/신고율, 이용자 신고 접수 | “광고/작업글”로 인한 패널티 감소가 목표일 때 |
| **실험** | 후기 삽입 유무에 따른 전환 차이, 키워드 밀도별 자연스러움/전환 | A/B 테스트 항목 후보 |

- 실제 수치는 카페·배포 환경에 따라 정의하면 됩니다. **무엇을 측정할지**만 문서에 고정해 두는 것이 중요합니다.
